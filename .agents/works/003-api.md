**Date**: 2026-10-31
**Auditor**: AI Agent (custom:nvidia/nemotron-3-ultra-550b-a55b)

## Executive Summary

The TTTaiga implementation has a **solid foundation** with a well-designed session-backed proxy (`api.php`), proper authentication flow, shared filter state management, and a functional UI. However, there are **critical gaps** in OCC/version handling for DELETE operations, missing usage of Taiga's native bulk endpoints, and incomplete metadata loading via `filters_data`.

**Overall Grade**: B- (Good architecture, critical OCC bug in bulk DELETE)

### What Works
| Component | Status | Notes |
|-----------|--------|-------|
| Session-backed proxy (`api.php`) | ✅ Correct | Stores token server-side, never exposes to browser |
| Login flow (`login.php`) | ✅ Correct | Calls Taiga `/auth`, stores token in `$_SESSION` |
| Token refresh on 401 | ✅ Partial | Proxy clears session on 401, but no auto-retry |
| Logout | ✅ Correct | Clears session, destroys cookie |

### Missing / Issues
- **No automatic token refresh retry**: When proxy gets 401, it clears session but doesn't attempt `/auth/refresh` before failing. User gets logged out immediately.
- **No `Accept-Language` header forwarding**: UI language preference not passed to Taiga.

## 2. OCC / Version Handling ❌ CRITICAL

### Current Implementation
| Operation | Version Sent? | Location |
|-----------|---------------|----------|
| Create (POST) | ❌ Not needed | N/A |
| Update (PATCH) | ✅ Yes | `Form.saveModal()` → `taigaExecuteBulkParallel()` |
| Delete (DELETE) | ❌ **NO** | `taigaExecuteBulkParallel()` only adds version for PATCH |
| Single Delete | ❌ Not implemented | Only bulk delete exists |

### Code Evidence
**`assets/taiga.js:1277-1279`** - Only adds version for PATCH:
```javascript
if (method === 'PATCH' && version !== null) {
    requestData = { ...requestData, version: version };
}
```

**Bulk delete calls** (e.g., `app-usors.js:168`) pass version in item data:
```javascript
selectedUsors.push({ id: $(this).val(), version: $(this).data('version') });
```
But `taigaExecuteBulkParallel` **ignores it for DELETE**.

### Impact
- Bulk delete will fail with `409 Conflict` or `400 Bad Request` on Taiga instances enforcing OCC
- Single delete not implemented at all
- No retry logic for version conflicts

### Required Fix
```javascript
// In taigaExecuteBulkParallel, line ~1277:
if ((method === 'PATCH' || method === 'DELETE') && version !== null) {
    requestData = { ...requestData, version: version };
}
```

## 3. Bulk Operations Analysis

### Current Approach vs Taiga Native Endpoints

| Operation | Current Implementation | Taiga Native Endpoint | Verdict |
|-----------|------------------------|----------------------|---------|
| **Bulk Create Usors** | Sequential individual POST in loop | `POST /userstories/bulk_create` | ❌ Should use native |
| **Bulk Create Epics** | Sequential individual POST in loop | `POST /epics/bulk_create` | ❌ Should use native |
| **Bulk Create Tasks** | Sequential individual POST in loop | `POST /tasks/bulk_create` | ❌ Should use native |
| **Bulk Create Memberships** | Not implemented | `POST /memberships/bulk_create` | ❌ Missing |
| **Bulk Update Usors** | Sequential PATCH via `taigaExecuteBulkParallel` | `POST /userstories/bulk_update_backlog_order`, etc. | ⚠️ Partial - only field updates, not ordering |
| **Bulk Delete** | Sequential DELETE via `taigaExecuteBulkParallel` | No native bulk delete | ✅ Acceptable (no native) |
| **Bulk Update Sprint Order** | Sequential PATCH | `POST /userstories/bulk_update_sprint_order` | ❌ Should use native |

### Bulk Create - Sequential vs Native
Current code (`app-usors.js:128-138`):
```javascript
stories.forEach(story => {
    TTTaiga.API.post('api.php/userstories', { ... })
});
```
**Problems**: 
- N network requests instead of 1
- No atomicity (partial success possible)
- Slower, more rate-limit prone

**Should use**: `POST /api/v1/userstories/bulk_create` with `{ "user_stories": [...] }`

### Bulk Update Order - Missing
Taiga provides specialized endpoints for ordering:
- `POST /userstories/bulk_update_backlog_order`
- `POST /userstories/bulk_update_kanban_order`
- `POST /userstories/bulk_update_sprint_order`
- `POST /userstories/bulk_update_milestone`

**Not used anywhere** in the codebase.

## 4. Metadata & Filter Data Loading

### Current Implementation
| Metadata | Current Method | Taiga Recommended | Status |
|----------|----------------|-------------------|--------|
| Statuses | Individual `/epic-statuses`, `/userstory-statuses`, etc. | `GET /{resource}/filters_data?project={id}` | ⚠️ Works but multiple calls |
| Milestones | `/milestones?project={id}` | Included in `filters_data` | ⚠️ Separate call |
| Points | Not loaded for usor forms | Included in `filters_data` | ❌ Missing |
| Members | `/memberships?project={id}` | Included in `filters_data` | ⚠️ Separate call |
| Epics (for usor) | `/epics?project={id}` | Included in `filters_data` | ⚠️ Separate call |
| Issue types/priorities/severities | Individual endpoints | Included in `filters_data` | ❌ Not loaded for issues |

### Code Evidence
**`assets/taiga.js:312-349`** - `taigaFetchStatuses` makes separate calls per status type.

**`filters_data` endpoint NOT USED** anywhere in codebase (grep returns 0 matches).

### Impact
- 4-6 API calls per form open instead of 1
- Inconsistent caching (5 min TTL for statuses, but no cache for others)
- Missing data in forms (points, issue types, etc.)

### Recommended Fix
```javascript
// Single call loads ALL metadata for a resource type
TTTaiga.API.get('api.php/userstories/filters_data', { project: projectId }, {
    success: function(data) {
        // data.statuses, data.milestones, data.members, data.epics, data.points, data.tags, ...
    }
});
```

## 5. API Proxy (`api.php`) Analysis

### What Works ✅
- Session-backed token forwarding
- CORS handling
- Request/response passthrough
- Caching for metadata endpoints (1hr TTL, 5min for memberships/users)
- Pagination header forwarding (`X-Pagination-*`)
- Auto-adds `member` filter to `/projects` from token payload
- HTML sanitization protection

### Issues ⚠️
| Issue | Severity | Details |
|-------|----------|---------|
| No request body for DELETE | High | Proxy forwards DELETE with no body, but Taiga requires `version` in body |
| No `Accept-Language` forwarding | Medium | User's language preference lost |
| Cache key doesn't include all query params | Low | Only `project` param used for cache key |
| No request validation/sanitization | Low | Passes through all headers/body |

### Critical: DELETE Body Handling
The proxy at `api.php:129` only sends body for non-empty `$input`:
```php
if ($input !== '') {
    $curl->opt(CURLOPT_POSTFIELDS, $input);
}
```
But DELETE requests from `taigaExecuteBulkParallel` send `data: undefined` (line 1289), which becomes empty string. **Version never reaches Taiga for DELETE**.

## 10. Code Quality Observations

### Strengths
- Clean separation: `taiga-core.js` (core), `taiga.js` (module-specific), per-module JS
- Shared filter state management is well-designed
- Form handling abstraction (`Form.saveModal`, `Form.populateDropdowns`)
- Caching strategy for metadata (5min TTL)
- HTML sanitization on all jQuery `.html()` calls

### Technical Debt
- **No TypeScript** - all JS, no type safety for API responses
- **jQuery-dependent** - hard to test, migrate to vanilla/Alpine?
- **Global state** (`window.taigaToken`, `window.apiUrl`, `TTTaiga.*`)
- **No API response typing** - assumptions about `status_extra_info`, `version`, etc.
- **Inline event handlers** in PHP partials (e.g., `onclick="..."`)
- **Mixed concerns** - API logic mixed with UI in module JS files

## 11. Recommended Architecture Improvements

### API Client Layer
Create a dedicated `TaigaClient` class/module:
```javascript
class TaigaClient {
    constructor(baseUrl, token) { ... }
    async get(endpoint, params) { ... }
    async post(endpoint, data) { ... }
    async patch(endpoint, data, version) { ... }
    async delete(endpoint, version) { ... }
    async bulkCreate(endpoint, items) { ... }  // Uses native /bulk_create
    async bulkUpdateOrder(endpoint, items) { ... }  // Uses native /bulk_update_*_order
    async getFiltersData(resource, projectId) { ... }
    // Auto-retry on 409 with version re-fetch
}
```

### Version Management
```javascript
// Every cached item stores version
class VersionedCache {
    get(id) { return { data, version } }
    set(id, data, version) { ... }
    invalidate(id) { ... }
}
```

### Shared Filter/Input Service
Already exists in `TTTaiga.State` and `TTTaiga.Filter` - formalize as service.

---

## 12. Conclusion

The TTTaiga codebase demonstrates **strong understanding of Taiga's domain model** and has a **well-architected proxy pattern**. The shared filter implementation aligns perfectly with the AGENTS.md vision.

**However, the OCC/version bug in bulk DELETE is a production blocker** for any Taiga instance with concurrency. The missing `filters_data` usage and native bulk endpoints are significant missed optimization opportunities.

**Recommended immediate action**: Fix the 3-line change in `taigaExecuteBulkParallel` to include version for DELETE, then prioritize native bulk endpoints and `filters_data` adoption.
